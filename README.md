# Debezium Server → Kafka vs RabbitMQ quorum vs прямое чтение WAL

Сквозной замер: четыре способа доставить строку из PostgreSQL получателю, у которого работа необратима.
Источник, полезная работа и схема идемпотентности у всех одинаковые, различается только конвейер доставки —
это и есть предмет замера.

```
NBomber, 200 отправителей ──POST /load/messages──► Web ──INSERT──► PostgreSQL (messages)
                                                                        │ логическая репликация, публикация load_test_pub
   ┌──────────────────────────┬────────────────────┬──────────────────┴──────────────────┐
   ▼                          ▼                    ▼                                     ▼
Debezium Server           Debezium Server     прямое чтение                  прямое чтение, шардированное
 (sink kafka)             (sink rabbitmq)     слот на получателя             64 шарда на advisory-локах
   │                          │                    │                                     │
топик, 2×N партиций      quorum-очередь            └──────────────────┬──────────────────┘
   │                          │                                       │
   └──────────────────────────┴────────── N получателей в load-test ──┘
              пачка 100 → claim в inbox → POST /send-email → offset / ack / LSN
```

Отправитель ничего не знает о транспорте: он зовёт веб-сервис, который просто пишет строку в таблицу.
«Полезная работа» получателя — вызов веб-сервиса, который ничего не делает: это изображает **необратимое
действие**, которое нельзя откатить вместе с транзакцией.

Оба CDC-плеча — один и тот же Debezium Server 3.6.2 с одинаковой конфигурацией источника, различаются только
приёмником. Значит, в цифрах остаётся разница конвейеров, а не движков.

## Одинаковые правила для всех четырёх

- **Полезная работа** — `POST /send-email` в соседний веб-сервис, внутри `Task.Yield()`.
- **Инбокс** — таблица в PostgreSQL без автовакуума. Пачка из 100 сообщений закрепляется одним запросом
  `insert … on conflict do nothing returning`, обрабатываются только те, что вернулись. Claim идёт до работы.
- **Подтверждение** — после работы: `StoreOffset` у Kafka, `basic.ack` у quorum-очереди,
  `SetReplicationStatus` у прямого чтения, раз на разобранную пачку.
- **Запись на диск** — у всех: Kafka по умолчанию, quorum-очередь через Raft и fsync, прямое чтение —
  обычный `insert` в таблицу инбокса.
- **Параллелизм** — у Kafka партиций вдвое больше числа получателей, у quorum-очереди одна очередь на всех,
  у прямого чтения по своему слоту на читателя.

Ключевая асимметрия, которую убрать нельзя: слот логической репликации не делится между читателями. Каждый
читатель получает весь поток WAL целиком, и право обработать строку разыгрывается в инбоксе. Плечо
`wal-sharded` снимает половину этого налога: строки делятся на 64 шарда по `id`, владение шардом — сессионный
advisory-лок, и в базу получатель ходит только за своими строками. Декодировать журнал целиком ему всё равно
приходится.

## Что из этого следует

**CDC-звено стоит около миллисекунды процессорного времени на сообщение.** Прямое чтение WAL при одном
получателе обходится в 1.19 мс CPU на сообщение, тот же путь через Debezium Server — 2.20-2.35 мс. Разница —
это сам Debezium: 46-76 процессорных секунд за прогон поверх всего остального, независимо от приёмника.
Плата за него не в скорости (по пропускной способности плечи сопоставимы), а в процессоре и в 550-700 МБ
памяти JVM.

**Цена CDC не зависит от числа получателей, цена веерного чтения — зависит.** У обоих плеч с Debezium
стоимость держится на 2.0-2.35 мс при любом N: декодирует журнал один процесс, получатели разбирают готовое.
У прямого чтения стоимость растёт с числом читателей — 1.19 → 1.21 → 1.48 → 1.88, потому что каждый читатель
декодирует журнал целиком: PostgreSQL тратит 64 процессорные секунды при одном читателе и 130 при восьми.
Пересечение уже видно на восьми получателях: 1.88 против 2.16 — дальше веерная схема становится дороже.

**Шардирование снимает налог на claim, но не налог на декодирование.** Веерный налог виден в отчёте двумя
числами: `skipped` у плеча `wal` равен ровно `(N−1)×M` — 700 000 лишних доставок на 100 000 сообщений при
восьми читателях, — а `ops/msg` растёт как `N/100`. У шардированного плеча `skipped` падает с 700 000 до 1044,
а `ops/msg` держится на 0.01. В процессорных секундах PostgreSQL это даёт 107 вместо 130 при восьми
получателях: заметно, но не радикально, потому что основную часть работы база тратит не на claim, а на
декодирование журнала в восьми walsender-ах.

**Kafka дешева по процессору, quorum-очередь дороже, и обе дешевле собственного клиента.** Брокер Kafka стоит
7-17 процессорных секунд за прогон, quorum-очередь RabbitMQ — стабильные 28-30 (Raft и fsync на каждое
сообщение). При этом веб-сервис и сам нагрузочный тест вместе стоят 52-71 секунды, то есть больше любого из
брокеров: стоимость HTTP-хопа и клиентских библиотек в реальном приложении будет того же порядка, что и
стоимость самой доставки.

**Пропускная способность на этом стенде упирается в отправителей, а не в конвейеры.** Вставка через веб-сервис
идёт со скоростью 4900-8000 сообщений в секунду, и уже на четырёх получателях конвейеры разбирают поток почти
в реальном времени: у `dbz-kafka` при восьми получателях после последней отправки остаётся 1.5 секунды работы.
Поэтому колонку `drain-only/s` нельзя читать как ёмкость конвейера — на больших N это скорость разбора
короткого хвоста, и она тем выше, чем меньше этот хвост. Сравнимое между плечами число здесь одно —
процессорные секунды на сообщение.

## Оговорки

- **Отправка у плеч идёт с разной скоростью**, и это не свойство конвейера: Debezium с его JVM отнимает
  процессор у веб-сервиса на той же машине, поэтому `send/s` у CDC-плеч 4900-5600 против 6900-8000 у прямого
  чтения. По этой же причине `drain s`, включающий фазу отправки, между плечами сравнивать нельзя.
- **Прогон `wal-sharded` на восьми получателях** выбивается: отправка заняла 32 секунды вместо обычных 14-20,
  p95 отправителя 147 мс. Восемь непулящихся соединений, раз в секунду опрашивающих `pg_locks`, плюс восемь
  walsender-ов — это заметная нагрузка ровно на том пути, по которому идут вставки.
- **Дрейф стенда за свип — −10.1%**: первая комбинация повторена последней, и она оказалась на 10% медленнее
  (3846 против 3457 сообщений в секунду). Разница между плечами меньше этой величины ничего не значит.
- **Сквозная задержка не публикуется.** При методике drain возраст сообщения равен половине времени разбора по
  построению, а часы PostgreSQL в контейнере и часы хоста расходятся на сотни миллисекунд. Честная задержка
  меряется отдельным прогоном на фиксированном темпе ниже насыщения — это другой замер.
- **Сбор метрик сам стоит ресурсов**: `docker stats --no-stream` запускается раз в секунду и занимает 1-2
  секунды, поэтому фактический период сэмплирования 2-3 секунды. Средние корректны, короткие пики могут не
  попасть в выборку.
- **Всё крутится на одной машине** (16 потоков, 31 ГБ): брокеры и Debezium в контейнерах, веб и тест —
  процессы рядом. Это сравнение стоимости, а не абсолютных потолков продакшена. Посторонние контейнеры на
  время свипа были погашены.
- **Восстановление после смерти воркера в `wal-sharded` не покрыто**: новый владелец шарда не досылает
  незавершённую работу предыдущего, потому что в пачечном инбоксе нет отметки `done`, а она стоила бы второго
  коммита на сообщение всем плечам. Схема рассчитана на передачу шарда между сообщениями.

## Изоляция прогонов

Ни один CDC-читатель не работает вне своего прогона: иначе тот, кто сейчас не под замером, продолжал бы
декодировать журнал и мешать соседям. Своего API у Debezium Server нет — конфигурация читается при старте,
поэтому прогон открывается стартом контейнера, а закрывается остановкой: позиция хранится в памяти
(`MemoryOffsetBackingStore`), слот дропается при выключении (`slot.drop.on.stop`), состояния не остаётся вовсе.
Управляет этим сам тест через `docker start` / `docker stop -t 30` — мягко, иначе слот переживёт остановку.

- **Топик** пересоздаётся на каждый прогон с `2×N` партициями и всегда **до** старта Debezium: топик, созданный
  брокером по первому сообщению, получил бы одну партицию, и весь свип упёрся бы в одного получателя.
  Метаданные при проверке запрашиваются по всему кластеру — запрос по имени топика при включённом
  автосоздании сам его создаёт.
- **Группа консьюмеров** одна на прогон и своя у каждого прогона. Именно группа делит партиции между
  получателями: по группе на копию каждый забрал бы весь топик, а прогон мерил бы одного получателя вместо N.
  Перед выпуском отправителей тест ждёт, пока каждому достанется ровно по `KafkaPartitionsPerConsumer`
  партиций и назначение устоится.
- **Exchange и quorum-очередь** создаются до старта контейнера: Debezium публикует без `mandatory`, и
  непривязанный routing key означал бы тихую потерю всего потока при внешне успешном прогоне.
- **Слоты** дропаются по префиксу до и после каждого прогона, `inbox`, `inbox_wal` и `messages` чистятся.
  Идентификаторы `messages` между прогонами **не** перезапускаются: сквозная нумерация значит, что хвост
  предыдущего прогона виден как чужой id, а не сходится по счётчикам тихо.
- **Отправители стартуют только после того, как слот начал стримить** (`pg_stat_replication.state =
  'streaming'`): записанное до появления слота в поток не попадёт вовсе.

В голове свипа идёт прогревочный прогон — он оплачивает JIT всего пути, пулы соединений и метаданные брокеров,
и в таблицы не попадает. В конце первая комбинация повторяется: это зонд дрейфа стенда.

## Как запускать

```bash
dotnet run --project AppHost
```

Дальше в дашборде Aspire запустить ресурс `load-test`. Параметры задаются аргументами:

```bash
--LoadTest:Transports=dbz-kafka,dbz-quorum,wal,wal-sharded --LoadTest:Consumers=1,2,4,8 --LoadTest:Messages=100000 --LoadTest:Producers=200
```

Результаты: сводные таблицы в `load-tests/results/results-*.md` и `.json`, отчёты NBomber по каждому прогону в
`load-tests/results/nbomber/` (в репозиторий не попадают). После каждого прогона обновляется
`results-latest.json`, поэтому прерванный свип не теряет уже собранное.

Старый бенчмарк из статьи (`/direct`, `/naive`, `/outbox`, `/replication`, `/debezium`) и его фоновые
консьюмеры выключены по умолчанию: слот `rep_slot` декодирует каждую транзакцию сервера, включая все вставки
прогона, а диспетчер outbox опрашивает базу каждые 100 мс — и то, и другое лежит прямо на измеряемом пути.
Включаются флагом:

```bash
dotnet run --project AppHost -- --Bench:LegacyConsumers=true
```
